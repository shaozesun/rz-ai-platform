### 2. 空间数据被推了**两套平行的 guid 树**

| | |
|---|---|
| **现象** | 同一空间推了两条记录，**名称完全相同**，只有 `guid` 不同；两套的 `path`/`parent_id` 各自自洽，形成两棵平行的树 |
| **证据** | `ems-config-space-rz` 实测 8 条记录 = 4 个空间 × 2 套 guid：<br>`-P006-0000-0000-000000000000` / `-P006-B001-…` / `-P006-B001-M002-F002R0010000` / `…R0020000`<br>`RZYWBXSJ-P006-0000-0000-000000000000` / `RZYWBXSJ-P006-B001-…` / `…F002R0010000` / `…F002R0020000` |
| **关键影响** | **设备与点位 100% 只挂在 `RZYWBXSJ-` 前缀那套上**（36 台设备只引用两个 `RZYWBXSJ-` 机房）；`-P006-` 那套**完全悬空**、无任何引用。若两套都入库，按机房聚合设备会把机房算成两个 |
| **我方期望** | ① 明确**哪一套 guid 为准**；② 作废那套是否发**删除事件**；③ 说明为何会出现两套（是否设备/点位重建导致 guid 变化）——这直接决定我们能否正确回溯历史 |
| **⚠️ 已造成事故（2026-10-12）** | 两套都入库后，`query_space_tree` 返回**两行同名空间**，而排序是 `ORDER BY path, name, guid` —— `-`(0x2D) < `R`(0x52) → **残缺那套排第一** → 模型拿它去 `query_devices` 得 `{"records":[],"total":0}` → **「问某机房有哪些设备/点位」全部返回空**（「空间 → 设备 → 测点」这条链在第一步就断） |
| **已做的止血（2026-10-12）** | ① 解析层加校验：**首段为空的 guid（形如 `-P006-…`）一律丢弃**（`models.py::_reject_truncated_guid`，抛 `SkippedRecord` → **计数但不入 DLQ**，日志显示「跳过=N」）；② 清理已入库的 4 行 `dcim_spaces` + 7 行 `dcim_spaces_history` |
| **备注** | ⚠️ 拦截**只解决"别入库"，不解决"为什么推两份"**。若对方后续澄清 `-P006-` 那套才是权威，我方必须**立刻撤掉这条拦截**（否则会把正确数据丢掉）。**这一条仍等对方口径。** |

### 18. 🔴 **同一 `(设备, 时间戳)` 被推两次、且两次的测点集合不同** —— 数据丢失

| | |
|---|---|
| **现象** | 同一台设备、**同一个时间戳**被打成两条消息推上来，且两条携带的 `points` **不同** |
| **证据（我方读 Kafka 原文实测，2026-10-08）** | 最近 10 分钟、一台设备：**88 个时间戳里 3 个被推了两次（3.4%）**<br>`ts=…773000`：`offset 533610` = `[HT_Hum, HT_Status_Comm]`；`offset 533612` = `[HT_Hum, HT_Temp, HT_Status_Comm]`<br>`ts=…123000`：`offset 533852` = `[HT_Temp, HT_Status_Comm]`；`offset 533857` = `[HT_Hum, HT_Temp, HT_Status_Comm]` |
| **为什么是数据丢失** | 我方时序库按 `(子表, 时间戳)` **后写覆盖**，而写入时**所有列都会写**（缺的写 NULL）。所以**只要"部分包"后到，就会把先到那条完整行的值覆盖成 NULL**。TDengine 的行是**整行不可变**的，没法只更新列 → 存储层解决不了<br>上面那次恰好是**完整包后到**（运气好）；反过来就丢 |
| **我方期望** | ① 确认这是设计如此还是实现副作用；② 能否保证**「同一时间戳只推一条」**，或**「后推的那条一定包含先推的全部测点」**；③ 若都不能，请明示（我方会在写入侧做合并，但那只能兜住"两条都在缓冲区里"的情况） |

# LLM 报告的稳定性：为什么「问题越改越多」，以及成熟做法（2026-10-24）

> 背景：跨期比较修复（2026-10-23 事故）完成后，本地实跑第一份真实报告，又发现两个新问题
> （`trend_guard` 倍数误杀、模型把 P50 写成「全场均值」）。用户追问：是不是机制有问题、
> 会不会每次都有新问题、业界成熟做法是什么。
>
> 结论：**确定性层可以做到稳定，文字表达层做不到"零缺陷"**。正确目标不是"让模型写得不出错"，
> 而是「把必须正确的部分移出模型 + 对剩下的部分度量，而不是赌它不出错」。

---

## 一、先把问题分类：三类缺陷，复发概率完全不同

| 类别 | 典型例子 | 根因 | 修一次会不会复发 |
|---|---|---|---|
| A. 确定性代码 bug | 日趋势轴线按各自日期集合建（10-15 事故）、上一期占比用本期分母（10-23） | 统计/取数代码写错 | **不会**，可单测锁定 |
| B. 输入表示缺陷 | 只给「本期占比 + 上期计数」→ 模型写 40−27=13 | 输入给了两把不同的尺子 | **不会**，换表示即消失 |
| C. 模型表达缺陷 | 把 P50 叫成「均值」、自己写两天的大小关系 | 语言表达方式无界 | **会**，只能压低概率 |

关键事实：**至今真正影响用户的错报（10-15、10-23）都是 A/B 类**，都已变成确定性规则或单元测试。
C 类目前造成的实际损失是「摘要少一条」（守卫丢弃），不是错话上线。

## 二、为什么感觉「越改越多」

1. **欠账在集中暴露**：确定性层（统计、出图）早有验证（两次运行逐字节一致），但**解读层
   直到第一次真调 LLM 跑完整报告才被真正执行**。之前只有组件单测与进程内模拟。
2. **发现率 ≠ 退化率**：发现得快是因为终于开始测这一层；确定性层没有出现新问题。
3. **守卫本身会产生新缺陷**：守卫是"已知错误模式的清单"，而表达方式是无界的。
   2026-10-24 的倍数误杀就是**守卫自己的 bug**（拿时长倍数去比日单量总量）。
   每加一条守卫，就多一个可能删掉正确结论的点 —— 所以守卫必须只针对**可证明为假**的句子，
   并且守卫自身要有 precision 测试。

一句话：**守卫是有界清单，模型表达是无界空间，靠加守卫追赶永远追不上。**

## 三、成熟做法（数据报告类的共识）

### 1. 语义层优先：算术与口径永远不交给生成模型

指标只定义一次，报告引用指标而不是让写手自己算/自己翻译。业界典型：
dbt Semantic Layer、Cube、Looker 的 LookML —— 同一指标在全组织只有一个口径。

本项目对应物：`report/facts.py`（把比较算好、坐标写全、编号成 F 句）。方向是对的，
只是目前只覆盖「按位置对齐、模型读不懂」的结构。

### 2. 事实类型化 + 引用绑定

每个数字连同**它的标签**一起作为不可拆的对象下发（`P50分钟: 114.9`、`均值分钟: 427.2`），
模型只能整句引用，不能把一个数按到另一个标签上。

本项目已有：`依据` F 编号校验（`_validate_section`）。
**缺口**：只校验"编号存在"，不校验"这句话里的标签与那个数字是否配对"——P50 那条正是从这里漏过。

### 3. 黄金数据集 + 快照回归

固定几份真实数据，每次改动后跑全流程，比对 stats/facts/渲染产物。
**A 类问题在这一步就死掉，不会流到线上。**

本项目：2026-10-24 新增 `report/tests/test_report_e2e.py`（五类各钉一份数据集）。

### 4. 离线评测量化表达层

固定 `stats`，真调模型 N 次，统计：被守卫丢弃句数 / 越界数字数 / 标签错配数 / 人工抽查通过率。
目标不是零缺陷，而是**知道缺陷率并把它压在一个可接受区间**。没有分母就只能被动救火。

本项目：**缺**。这是下一步最有价值的一件事（成本：每次评测消耗若干次 LLM 调用）。

### 5. 分级保证 + 按风险决定是否人审

- 数字与关系：必须确定性正确（A/B 类 + 守卫）；
- 解释与建议：允许措辞不完美（C 类，靠提示词与度量）；
- 高利害报告：保留一道人工复核，比让模型自检便宜且可靠。

**为什么不上 reflection（写完再自检）**：模型调用 8 → 16 次，报告耗时直接翻倍；
且模型没有第二个数据源，"维度/标签弄混"这类错自检同样查不出，只会提高措辞层面的挑刺率。
2026-10-23 已否决过一次。

## 四、本项目现状与差距

| 能力 | 现状 | 差距 |
|---|---|---|
| 确定性统计与出图 | ✅ 两次运行逐字节一致 | — |
| 对齐型结构事实化 | ✅ `facts.py`（编号 + 依据校验） | 只覆盖对齐型；标签维度未校验 |
| 可证伪守卫 | ✅ `trend_guard` 16 项 / `compare_guard` 14 项 | 守卫自身缺 precision 测试（10-24 误杀） |
| 端到端回归 | ✅ 2026-10-24 新增 `test_report_e2e` | 依赖本机 `data/analysis`，非 CI |
| 表达层缺陷率度量 | ❌ 无 | 详见待办 |

## 五、已落地（2026-10-24）

1. `trend_guard._check_multiples`：倍数只在**基数对得上**时判定（日期锚点 → 同日上期值；
   明说总量 → 周期总量；其余不猜）。补 2 项自检（14 → 16）。
2. `narrate._RULES`：P50/P90/P95 与「均值/平均值」不得互称，引用照抄 JSON 键名。
3. `report/tests/test_report_e2e.py`：五类报告各钉一份真实数据集，
   比对 `stats` / `facts` / 图名集合 / HTML 哈希；`--update` 重建快照；无数据 SKIP。

## 六、待办（未做）

1. **标签维度引用校验**：要求"均值/平均"类措辞必须引用 `均值分钟` 键，
   "中位/P50"必须引用 `P50分钟`——把第三节第 2 条补齐。
2. **解读层评测脚本**：同一份 stats 跑 N 次真 LLM，统计丢弃率/越界数字/标签错配，形成基线。
   有了基线，"这轮改动是否让质量变好"才有判据。
3. **守卫精度测试**：每条守卫都要有"正确句子不得被删"的用例（本轮 trend_guard 已补 1 条方向）。
4. `test_report_e2e` 的快照能否进 CI：需要脱敏小样本；当前依赖本机数据，只做运维闸。
5. **把高频派生值预先算好**（2026-10-24 实跑证据）：`_audit_numbers` 报了 4 处"统计里没有的数字"，
   逐个核对后**都是模型自己算对的**，但违反了"不许换算"——`74%`＝33.3+41.0（专业合计占比）、
   `84%`＝64/76（提前≥1天占比）、`32 小时`＝`start_delay.p50` 1958.8 分钟。根治不是加守卫，
   而是在 compute 里直接给出这些汇总与可读时长（`start_delay` 目前没有 `readable` 字段）。

## 七、边界（明确不做）

- 不追求文字层零缺陷：表达空间无界，成本不可控。
- 不为"可能错"的句子加守卫：只拦**可证明为假**的（否则误杀正确结论，代价更大）。
- 不引入 reflection / 解读层沙箱：见第三节第 5 条与
  `docs/problems/report-cross-period-comparison.md` 第四节。

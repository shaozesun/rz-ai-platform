# 联网调研

## 何时用

- 需要**外部公开信息**：厂商/产品资料、技术标准与规范、行业动态、通用概念、横向对比
- 题目需要多角度交叉验证（「X 是什么 / 怎么做 / 现状如何 / A 和 B 比怎么样」）
- 需要外部信息支撑的产出（报告、方案、看板）

**不要用**：内部数据查询（工单/资产/容量/人员）走内部平台工具；本技能只管外部信息。

## 核心原则

**绝不只搜一次就开始写。** 输出质量 ≈ 证据质量，而单次搜索永远不够。

- 证据不足就继续检索，**不要凭印象补全**
- 内部事实（平台数据）与外部信息**分开陈述**；两者冲突时以内部数据为准并说明差异

## 四阶段

### 阶段 1 · 广度扫描

先搜主题全貌 → 识别出 2-4 个关键维度 → 记下存在的不同视角/立场。
例：查「某类设备某故障」→ 维度可能是：成因、主流处置方式、厂商建议、行业规范。

### 阶段 2 · 逐维度深挖

- 每个维度**换不同措辞搜 2-3 次**（同义词、中英文、术语全称与缩写）
- 摘要不够就用 `web__fetch` 读原文 —— **重要来源必须读全文**，不要只吃 snippet
- 来源里提到别的关键资料 → 继续追

### 阶段 3 · 多样性与验证

| 信息类型 | 目的 | 查询词示例 |
|---|---|---|
| 事实与数据 | 具体证据 | 「数据」「统计」「规模」「占比」 |
| 案例 | 真实落地 | 「案例」「实践」「实施」 |
| 专家观点 | 权威视角 | 「专家分析」「解读」「白皮书」 |
| 趋势 | 方向判断 | 「2026 趋势」「预测」「演进」 |
| 对比 | 备选与权衡 | 「对比」「替代方案」「区别」 |
| 局限与批评 | 平衡视角 | 「问题」「局限」「风险」「挑战」 |

关键结论要有 **≥2 个独立来源**；主动去找反面证据，不要只收有利信息。

### 阶段 4 · 综合前自查

- [ ] 至少 3-5 个不同角度都搜过？
- [ ] 重要来源读过全文，而不是只看摘要？
- [ ] 有具体的数据、案例、专家观点？
- [ ] 反面与局限也覆盖了？
- [ ] 信息是当前的、来源是权威的？

**任一项为否 → 回去继续检索，不要开始写。**

## 查询技巧

- **具体化**：❌「AI 趋势」 → ✅「2026 企业级 AI 落地 趋势」
- **带权威源提示**：加「白皮书」「标准」「厂商文档」「官方文档」「研究报告」
- **带内容类型**：加「案例」「数据」「对比」「局限」
- **时间精度按问题选**（用**本轮消息前缀里的「当前时间」**，不要凭记忆猜年份）：

  | 用户问的是 | 需要的精度 | 查询写法示例 |
  |---|---|---|
  | 今天 / 刚发布 | **年月日** | `2026年9月16日 发布` |
  | 这周 | 周范围 | `2026年9月第3周` |
  | 最近 / 最新 | **年月** | `2026年9月 更新` |
  | 今年 / 趋势 | 年 | `2026 趋势` |

  只写年份**搜不到「今天」的消息** —— 问「今天」就必须带月日。
- 同一问题换语言/写法各搜一次（中文一次、英文一次往往结果不同）

## 何时读全文（web__fetch）

- 搜索结果高度相关且来源权威
- 摘要不够，需要具体数据、参数、案例细节
- 需要看完整上下文才能判断可信度

## 引用规范（硬性）

- 引用外部来源的每个论断，**句后就紧跟** `[citation:标题](URL)`
- 回答**末尾**加一段「Sources」，用普通 markdown 链接逐条列出：`[标题](URL) - 一句说明`
- 内联用 `[citation:…]`，Sources 段用普通链接 —— 两者不要混用
- 不要写没有引用的外部内容，**不要编造 URL**，不要引用自己没读过的来源
- 引用只保证**来源可查**，不保证内容正确；来源互相矛盾时并列说明，不要挑一个当定论

### 具体事实必须落地（最常犯的错）

**标准号、发布/实施年份、法规条款、统计数字**这类**看起来权威的具体事实**，必须能在**本次抓取的正文里找到**才写：

- ✅ 抓到的正文里写了 `GB 50174-2017`，则引用并附来源
- ❌ **不要凭记忆写**「GB55037-2026」「ISO 3941:2026」这种带年份的具体编号——年份极易记错，写错了比不写更糟（该标准可能是 2022 年发布的）
- 找不到就两种处理：① 换措辞再检索/抓原文；② 明确写「**该标准号/年份未核实**」，不要写成确定事实

**预测与目标数字**（如「效率提升 50%」「收敛率≥85%」「MTTR 降低 40%」）**本质上没有来源**，因此：

- 必须标注为「**建议**」或「**估算**」，并给出**推导依据**（基于哪部分内部数据、怎么算出来的）
- **禁止**写成既成事实或行业共识（如「业界普遍达到 85%」却没来源）
- 宁可给区间 + 依据（「建议目标 80%-85%，依据：当前 A1 分部工单密度 X / 同类改造案例 Y」），也不要给一个没来由的精确数字

### 公司信息缺失时

公司战略方向、组织架构、预算口径、考核指标这类**公司特有内容**，只有用户提供或 `skill__company_profile`（公司背景档案）里写着才能写。**都没有时不要用通用行业模板替公司下结论**——要么向用户索要「公司当前的重点方向 / 团队与预算约束」，要么在报告里明确标注「**需公司输入**」。

## 交付形态（回答与成品分开）

**对话里的回答**：结论摘要 + 关键发现（每条带内联引用），几句话说清结论。**不要把长报告正文糊在对话里。**

**成文成品**：调研结论多、篇幅长、要给别人看，或用户要「报告/方案/对比分析」时，把成品落成文件再交付。联网调研**没有数据集**，用保留的工作区写：

```
analysis_write_file(dataset_id='workspace', path='调研报告.md', content=<完整 Markdown>)
```

返回值里带服务端生成的 `url`，**逐字符复制**它输出一行：

```
<file url="<上面返回的 url>" name="调研报告"/>
```

- 文件里放**完整正文 + Sources 段**，结构：结论摘要 → 分维度分析 → 对比与权衡 → 局限与不确定 → Sources
- 对话回答**只给摘要**，不要再把全文贴一遍
- 用户明确要 PPT / PDF / Word / Excel / 看板 → 走系统提示「报告生成规范」的流程（那条路基于数据集，需先 `analysis_load` 物化数据）
- 后续要改报告：`analysis_str_replace(dataset_id='workspace', ...)` 或重写；`analysis_read_file` / `analysis_ls` 可回看工作区

**不用落文件的情况**：问答式调研（如「某标准怎么规定的」）、结论本身就短 → 直接在对话里答完。

一句话判据：**回答给结论，成品给文件；同一份内容不要既糊在对话里又写进文件。**

## 常见错误

- ❌ 搜 1-2 次就下结论
- ❌ **同一个 query 重复搜**（换角度要换措辞；一个维度 2-3 次没有新信息就转下一维度，重复搜只会白耗时间并撑大上下文）
- ❌ 只看摘要不读原文
- ❌ 只搜一个角度就动笔
- ❌ 忽略反方观点与局限
- ❌ 拿过时信息当现状（问「今天」却只写年份）
- ❌ 把网页上的说法当内部事实讲出去
- ❌ 编造 URL / 引用没读过的来源
- ❌ 把整篇调研报告直接写进对话回答（该落文件的成品要和回答分开）

## 长调研的上下文管理

调研轮次多、网页正文长，中途可能触发上下文压缩（被删消息的原文会归档，可回读）：

- **每完成一个维度**，用几句话小结该维度的「结论 + 来源 URL」——结论留在对话里，细节可以只留来源
- 想引用某个具体数字/名称却记不清时，用 `history_search` 检索、`history_read` 读回原文，**不要凭印象写**
- 中间笔记、对照表可落到沙箱文件（`analysis_write_file`），后续按需读回

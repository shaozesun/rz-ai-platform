# 审查技能

给一个技能做质量审计，产出**能直接照改**的意见（不是"建议改进"这种空话）。

## 看什么

### 一、先看确定性的（能一眼判定，别靠感觉）

| 项 | 判据 |
|---|---|
| frontmatter | 只含 `name`/`title`/`description`/`category`/`domain`/`kind` 六字段；`name` 为 `^[a-z0-9_]+$` 且 ≤64；`description` 非空、不含 `<` `>`、≤1024 |
| 正文 | 非空；有明确的「步骤/流程」而不是只有口号 |
| 资源索引 | 正文引用的 `references/*.md`、`templates/*` 是否**真的存在**；`references/` 里的文件是否被正文指到 |

### 二、再做质量判断（逐项给结论，不留空）

| 维度 | 要问的问题 |
|---|---|
| **触发** | description 覆盖的是**真实用户话术**吗？会不会太窄（用词只有作者自己会说 → 永远不触发）或太宽（会把别的活抢过来）？把用户可能说的 3~5 种说法对照一遍。 |
| **边界** | 有没有写清**非目标**——什么情况**不该**用本技能？没有边界 = 模型会在不该用的地方用。 |
| **可执行** | 正文是**可照做的步骤**（做什么、什么条件、输出成什么样），还是"要严谨、要重视、注意质量"这类无法执行的话？后者一律标 🔴。 |
| **时效** | 有没有写死的会过期的值：具体人名、版本号、额度、日期、一次性链接？应改为"从工具/接口取"。 |
| **重叠** | 与已有技能是否重复或大部分重叠？重复应**合并进已有技能**，而不是并存（两个都能触发时模型会摇摆）。 |
| **篇幅** | 超过 ~500 行时是否该拆到 `references/`？拆分后正文有没有指明**何时去读**哪一份？ |

## 输出规范

- 按 **🔴 阻塞 / 🟡 建议 / ⚪ 可选** 分级，每一项写清：**问题 → 为什么是问题 → 怎么改**。
- **怎么改必须是可直接执行的**：给出 `skill_manage(action='patch', name=…, find=…, replace=…)`
  的原文片段（find 要能在现有正文里唯一命中），不要只说"建议补充触发词"。
- 最后一行给结论：**可以上线 / 改完 🔴 再上线**。
- 没问题就直说没问题，**不要为了凑数编问题**；也不要把 🟡 说成 🔴（分级要诚实）。

## 约束

- **只读不改**：本技能只产出审查意见，**不得**替用户改技能；用户确认后再由
  `skill_manage` 执行（edit/patch）。
- 读技能的方式：
  - **本人自建技能** → `skill_manage(action='list')` 列出，`skill_manage(action='read', name=…)` 读全文；
  - **公开技能** → `skill__<技能名>`（如 `skill__chart`）取正文。
- 审计公开技能时要说明：公开技能由开发侧随代码维护，用户改不了，提意见要落到
  「我们把这条改掉」，而不是让用户去改。
- 不要顺手评价技能"好不好用"这类主观感受——只按上表逐项给可验证的结论。

# 数据分析

把沙箱里的数据集算成有信息量的聚合结果。本技能管**怎么算**；**怎么画**（选图型、字段怎么摆）
由 `skill.chart` 负责——两边别搅在一起。

## 工作流

1. `analysis_load(capability_id, params)` 物化**全量**到沙箱（原始记录不进上下文）。返回值里有列名、
   类型（dtypes）、预览样例，以及 **`analysis_shapes`——按本数据集实际列算得出的分析形状**，写代码前先看它。
2. **先定分析形状，再按形状写聚合**——不要先跑 `value_counts` 看手里剩什么形状，那样只会出柱/条/饼。
   先想清楚这块数据要表达什么（趋势/对比/占比/分布/关系/交叉），再回到沙箱按该形状需要的字段写代码
   （如要画耗时分布先 `pd.cut` 分箱，要画「专业 × 级别」先 `groupby(['专业','级别']).size()` 得每组一行三列）。
3. 一次 `analysis_exec` 把**全部**聚合算完，赋给变量 `result`；多组结果放进 dict
   （`result = {'专业分布': 表1, '时间趋势': 表2}`，chart_data 按该 dict 原样返回）——不要每个维度各跑一次
   exec（每次都是新子进程，明显更慢）。算完交给 `skill.chart` 选图型。

## 分析目的 → 数据形状 → pandas 写法

| 分析目的 | 要产出的数据形状 | pandas 写法示例 | 对应图型 |
|---|---|---|---|
| 各类别数量对比 | 类别 + 数值 | `df['专业'].value_counts().reset_index(name='数量')` | column / bar |
| 占比构成 | 类别 + 数值 | 同上（**默认实心饼图**，不加 `donut`） | pie |
| 时间趋势 | 时间 + 数值（按时间升序） | `df.groupby('日期').size().reset_index(name='数量').sort_values('日期')` | line / area |
| 两个分类维度交叉 | 每组一行三列 | `df.groupby(['专业','级别']).size().reset_index(name='数量')` | 堆叠 / 分组 column |
| 单个数值字段的分布 | 一列数值（可先分箱） | `pd.cut(df['处理时长'], bins=8).value_counts().reset_index(name='数量')` | histogram / boxplot |
| 两个数值字段的关系 | 两列数值 | `df[['温度','负载']].dropna()` | scatter |
| 多个指标对比 | 每个对象一行、多指标多列 | `df.groupby('专业')[['工单数','已关闭数']].sum().reset_index()` | radar |
| 流向 / 转化 | 源 + 目标 + 数值 | `df.groupby(['来源','去向']).size().reset_index(name='数量')` | sankey / funnel |
| 文字频次 | 词 + 权重 | 分词计数后转两列 | word_cloud |

**不要一律只做 `value_counts`**——它只产出「类别 + 数量」两列，从这一种形状出发永远只能出柱/条/饼。
数据里存在可用的数值字段（耗时/温度/容量/金额/次数）时，先判断它适合出分布类还是关系类图，再决定怎么算。

## 交互表格视图整理（列表 >20 条时出 `<file records_url>`）

明细总数 >20 条时走「物化 → 整理 → 出交互表」三步（对应系统提示词元规则 2）：

1. `analysis_load(同一能力、同一筛选参数)` 物化**全量**数据到沙箱，拿到 `dataset_id`（原始记录不进上下文）。**本工具不给 `records_url`**——URL 要等第 2 步整理成功才发。
2. `analysis_exec(dataset_id, ...)` 把 df 整理成可读视图，**固定存为 `view.csv`**（`df.to_csv('view.csv', index=False)`）：

   - **整理前先看 `analysis_load` 返回的预览样例**，确认真实字段结构与取值，再写重命名/取值/映射；**不要凭猜测硬编码字段 key，也不要按数字硬转**。
   - 字段名改成**中文表头**；只保留有意义的关键列；编码列（状态/类型/等级等）按业务含义解码成中文标签。
     已知稳定映射：专业 specialty `1=供配电 / 2=制冷 / 4=智能化 / 8=其他`；故障阶段 stage `-1=驳回期 / 7=故障派发 / 2=故障处理 / 3=故障验收 / 5=故障关闭`。
     其余枚举按你从该能力描述见过的 code→含义转换（不确定的列宁可去掉，也别留数字码）。
   - **对象型列**（如 发起人/审批人 是 `{userId,name,headimg}` 这类 JSON）只保留其中的名称字段（name/姓名/label），不要整段输出 JSON。
   - **只含内部 ID 的列**（列名含 id/uid/编号、值是不可读长数字且没有配套名称列）不保留。
   - **整理后必须自检**：保留的列若**整列（或绝大多数）为空**，说明取值/映射写错 → 修正映射或用原始列兜底，**绝不允许交付整列为空的列**；不确定的列宁可删掉。
   - `view.csv` 是保留文件名，会被自动剔除、不作为下载产物——不要另存成别的 .csv 当交付。
3. 用**第 2 步 `analysis_exec` 整理成功、写好 `view.csv` 后返回的** `records_url` **原样**输出一行 `<file url="<records_url>" name="<能力名>列表"/>`（url 逐字符复制，禁止改写）。右侧表格优先展示 `view.csv` 的整理结果，所以不要直接展示原始英文字段。

**`records_url` 只在 `view.csv` 整理成功后才由 `analysis_exec` 给出（`analysis_load` 不给）**；没物化 / 物化失败 / 整理失败 / 没拿到真实 url 时一律不输出 `<file>`、绝不编造。

## 约束

- data 必须忠于工具返回结果，禁止编造或改写数值
- 编码列（状态/类型/等级等）按业务含义解码成中文；不确定含义的宁可去掉，也不要留数字码，更不要编造标签
- 多维度数据每个维度一张图时，维度选 2-3 个最有信息量的，不要堆砌；**也不要清一色只用柱/饼**

# 告警响应超时

「谁还没响应」的固定口径查询：**告警发生超过 5 分钟、仍未解除、重要及以上、
且没有关联的处置工单**。这是平台标准，被问到就直接按它查，
**不要反问「几分钟」「什么级别」**。

## 一、标准口径

四个条件同时成立才算一条：

| 条件 | 字段 |
|------|------|
| 发生超过 5 分钟 | `alarm_time` 距今 > 5 分钟（按**发生时间**算，不是建单/响应时间） |
| 仍未解除 | `status <> '3'`（只看状态，**不看解除值是不是 0** —— 未恢复时对方给哨兵 0） |
| 重要及以上 | `alarm_level >= 重要`（重要 + 紧急） |
| 没有关联处置工单 | `dcim_alarm_orders` 里查不到关联该告警（`event_log_id = guid`）的单 |

**为什么查工单就是查响应**：人员点「响应」会自动建立告警工单，所以有单 = 已响应，
没单 = 没人响应。不需要再去分辨工单里填没填响应时刻。

## 二、查询

```
dcim_meta__query_alarms({'unresponded_min': 5, 'level': '重要'[, 'park': '廊坊']})
```

- `unresponded_min` 与 `level` **两个必须同时传**，少传就是把口径放宽了。
- 有园区加 `park`（如「廊坊」）。默认**不加时间窗** —— 这是当前快照；
  用户明确问某天/某班次才加 `start_ms`/`end_ms`（裸日期，`end_ms` 含当天整天）。
- **不要传 `status`**：`unresponded_min` 已自带 `status<>'3'`，
  再传 `recovered` 会把它改成「已恢复」，查成 0 条。
- 直接引用返回的 `total` 作为条数；`records` 只是当页（工具层钳到 20 条）。

## 三、交付

- **0 条就是没有**，直接说「当前没有告警响应超时」，不要换参数反复重拉。
- ≤20 条：回答里用 Markdown 表格（园区 / 空间 `space_name` / 设备 / 测点 / 级别 / 告警时间），
  持续时长能算就写「已 X 分钟」。
- >20 条：`analysis_load('dcim_meta.query_alarms', {...同上})` 物化全量 → 一次
  `analysis_exec` 整理成可读视图（地点用 `space_name`，保留设备 / 测点 / 级别 /
  告警时间 / 持续时长）→ 输出 `<file url=.../records>`。
  **持续时长在沙箱里算**，不要让模型心算。
- 只有用户明确要 Excel/导出时才产文件。

## 四、别混「已响应但慢」

`query_alarm_orders` 的 `response_timeout_min=N` 筛的是**已经响应、但响得晚**的单
（响应时刻 − 告警时刻 > N 分钟）。只在用户明确说「响应了但很慢 / 响应超过 N 分钟」时才用；
问「告警响应超时 / 没人管 / 还没响应」一律走本技能。
